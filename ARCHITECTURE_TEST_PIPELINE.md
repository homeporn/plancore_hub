# PlancoreAI — Пайплайн тестирования и аудита архитектуры

Цель: перед перезапуском разработки получить объективную карту архитектурного
долга, построить регрессионную «страховочную сетку» и поставить CI-ворота,
которые не дадут долгу расти. Документ организован как **последовательный
конвейер из фаз**: каждая фаза имеет вход, инструменты, что именно ищем
(красные флаги, специфичные для этого кода), и критерии выхода.

Стек проекта: React 18 + TypeScript + Vite + Tailwind/shadcn + Supabase
(Postgres + Auth + Edge Functions), Zustand + React Query, Vitest.

---

## Фаза 0. Фиксация «источника истины» (branch consolidation)

**Проблема:** есть `main` (≈184 файла) и десятки веток `codex/*`
(самая полная — `codex/volume-labor-followup`, ≈214 файлов), плюо `billing`,
`account-editing`, `landing`, `grid-gantt-performance`. До любого
тестирования нужно зафиксировать, что считаем кодовой базой релонча.

Шаги:
1. Свести diff всех живых веток к `main`: `git log --oneline --graph --all`,
   `git diff --stat main..origin/codex/<branch>` для каждой.
2. Построить матрицу «фича → ветка → статус (готово/наполовину/мертво)».
3. Выбрать одну интеграционную ветку (кандидат: `codex/volume-labor-followup`)
   и влить в неё нужные фичи; остальные ветки — заархивировать тегами.
4. Зафиксировать lock-файлы: оставить **один** менеджер пакетов
   (сейчас есть и `bun.lock`, и `package-lock.json` — это рассинхрон рисков).

**Выход:** одна ветка `develop` как единый источник истины; решение по
менеджеру пакетов; список «фич в подвешенном состоянии».

## Фаза 1. Статический анализ и здоровье типов

Запускается на зафиксированной ветке, до правок.

Инструменты и проверки:
- `tsc --noEmit` со **строгим** конфигом-зеркалом. Сейчас в `tsconfig`
  отключены `strictNullChecks`/strict — это маскирует целый класс багов на
  `Date | null`, которыми пронизан `ScheduleRow`. Завести `tsconfig.strict.json`
  и посчитать число новых ошибок — это и есть метрика типового долга.
- `eslint .` + правило на циклические импорты.
- **`dependency-cruiser`** или `madge --circular src` — карта зависимостей
  модулей. Ищем: циклы, «бог-модули», обратные зависимости `lib → components`.
- **`knip`** или `ts-prune` — мёртвый код, неиспользуемые экспорты, дубликаты
  утилит (ожидаемо много после нескольких генераторов).
- `npm run build` + анализ бандла (`rollup-plugin-visualizer`): размер чанков,
  что тянет xlsx/jspdf в основной бандл, корректность code-splitting по роутам.

Красные флаги именно здесь:
- бизнес-логика, импортируемая из UI-компонентов и наоборот (нет слоя домена);
- две реализации одного и того же (несколько конвертеров дат, дублирующиеся
  расчёты длительности в `scheduleEngine`/`cpmEngine`/`calculationService`).

**Выход:** отчёт `static-analysis.md` с числами (ошибки strict, циклы,
мёртвые экспорты, топ-10 крупнейших модулей) + граф зависимостей (svg).

## Фаза 2. Регрессионная сетка вокруг доменного ядра

Перед рефакторингом фиксируем поведение «золотыми» тестами — чтобы перезапуск
не сломал расчёты. Ядро (чистые функции, тестируется без UI и без сети):

| Модуль | Что покрыть |
|---|---|
| `cpmEngine.ts` | прямой/обратный проход, ES/EF/LS/LF, общий и свободный резерв, критический путь, **детекция циклов**, все типы связей FS/SS/FF/SF, отрицательные лаги, вехи (0 дней), задачи в работе (remainingDuration) |
| `auditEngine.ts` | по одному кейсу на каждое правило (СДР, имена, связи, орг/отдел, даты, длительности); счётчики critical/warning/info/passed/failed |
| `scheduleEngine.ts` | каскадное распространение дат, агрегация заголовков |
| `scheduleConverter.ts` | round-trip `TaskRow → ScheduleRow → TaskRow` без потерь (это самое опасное место — двойная модель) |
| `forecastEngine`/`progressEngine`/`statusEngine` | SPI/SV, прогноз задержки, граничные значения |
| `calculationSyncService.ts` | расчёт трудозатрат с факторами, состояния sync (synced/outdated/overridden) |
| `excelParser.ts` | недостающие колонки, пустой файл, мусорные даты, локали |

Методики:
- **Golden/snapshot-тесты** на реальных Excel-графиках (собрать 3–5 эталонных
  файлов: маленький, большой, с циклом, с битыми связями).
- **Property-based** (fast-check) для CPM: для случайного DAG общий резерв
  критических задач = 0; добавление ребра не уменьшает длительность проекта;
  топосортировка не теряет узлы.
- **Кросс-проверка инвариантов**: длительность проекта из CPM == max EF;
  audit на сгенерированном «идеальном» графике даёт 0 critical.

**Выход:** покрытие доменного `lib/` ≥ 80% строк; набор эталонных входов в
`src/test/fixtures/`; CI-порог на покрытие ядра.

## Фаза 3. Целостность модели данных и БД

Здесь ловим главный системный риск — **дрейф между миграциями Postgres,
автогенерёнными типами Supabase и доменными типами фронта**.

Проверки:
1. **Схема vs типы:** прогнать `supabase gen types` на актуальной БД и
   сравнить с закоммиченным `src/integrations/supabase/types.ts`. Любой diff —
   это незакоммиченная/ручная правка схемы.
2. **Миграции применяются с нуля:** поднять чистую Postgres (Supabase CLI или
   docker), применить все миграции по порядку — упадёт на любой
   несогласованности (порядок, дубли таблиц, забытые enum).
3. **Карта таблица → фронтовая модель.** 44 таблицы, но фронт активно
   использует `ScheduleRow`/`TaskRow` с собственными именами полей
   (camelCase vs snake_case, `predecessors` как jsonb). Составить таблицу
   соответствий и пометить рассинхроны (поля, которые есть в типе, но не
   пишутся в БД, и наоборот).
4. **Покрытие RLS:** скрипт, который проверяет, что на **каждой** таблице с
   `project_id` включён RLS и есть политики SELECT/INSERT/UPDATE/DELETE через
   `is_project_member`. Таблицы без политик — критическая дыра.
5. **Версионность:** проверить логику `schedule_versions`/`calculation_versions`
   (флаг `is_current` единственный на проект, ссылки baseline не висячие).

**Выход:** `data-model-audit.md` с матрицей соответствий и списком таблиц
без RLS / без политик / с дрейфом типов.

## Фаза 4. Аудит состояния и потоков данных (frontend)

Архитектурно самое слабое место Lovable-кода — управление состоянием.

Что ревьюим (полу-ручно + линт-правила):
- **Машина режимов `Index.tsx`** (`AppMode` из 9 состояний): где
  source-of-truth по `scheduleRows`, нет ли рассинхрона между локальным
  состоянием и Supabase, что происходит при перезагрузке.
- **Двойная модель `TaskRow`/`ScheduleRow`** и ручные `merge*`/`convert*` —
  кандидат №1 на устранение (одна модель + проекции).
- **Zustand-сторы** (logic-graph/store, ProjectProvider): дублирование
  серверного состояния, отсутствие нормализации.
- **React Query**: ключи кэша, инвалидция после мутаций, оптимистичные
  апдейты в `calculationSyncService` — гонки и устаревший UI.
- **localStorage-черновики** (`scheduleStorage`): конфликт «черновик vs
  сохранённый проект».
- Гигантские компоненты (`ScheduleTable` 924, `CalculationWorkspace` 1279,
  `ScheduleView` 717) — измерить цикломатическую сложность, наметить распил
  на контейнер/презентацию/хуки.

**Выход:** `state-architecture-review.md` с диаграммой потоков данных и
приоритезированным списком рефакторингов (P0/P1/P2).

## Фаза 5. Интеграционные и E2E-сценарии

Инструмент: **Playwright** (демо-режим без логина даёт быстрый вход —
`localStorage.plancoreai_demo`). Критические пути:

1. Загрузка Excel → авто-аудит → вкладки результатов → экспорт PDF/XLSX.
2. Конструктор: создать строки, проставить связи, запустить аудит, дерево СДР.
3. Логический граф: добавить связь, увидеть критический путь, диагностику цикла.
4. Мастер генерации → конструктор → аудит.
5. (Авторизованный) загрузка как новая версия проекта → changelog → baseline →
   variance.
6. Расчёт трудозатрат: элемент → work item → синхронизация в график.

Для каждого: позитивный путь + ключевой негатив (битый файл, граф с циклом,
пустой проект). Проверяем отсутствие необработанных исключений и зависаний.

**Выход:** набор Playwright-тестов на ~6 джорни в CI (на демо-данных).

## Фаза 6. Безопасность

- **RLS по факту** (а не только наличие политик): тесты, где пользователь A
  пытается читать/писать проект пользователя B — должно быть запрещено.
- **Edge functions** (`ai_agent`, `telegram-bot`, `recalc-assignments`,
  `project-status-context`): проверка авторизации входящих запросов,
  валидация payload, обработка ошибок внешних API.
- **AI-агент:** prompt-injection — пользовательские данные графика попадают в
  промпт; проверить, что tool-calling не даёт изменять чужие проекты.
- **Секреты:** греп по репозиторию на ключи (`run_secret_scanning`),
  проверка, что anon-key и URL Supabase не утекают лишнего, env-разделение.
- **Демо-режим:** убедиться, что он не открывает доступ к серверным данным.

**Выход:** `security-review.md` + автотесты cross-tenant доступа.

## Фаза 7. Производительность и масштаб

- CPM/аудит на графиках 1k / 5k / 20k строк — замер времени, поиск O(n²).
- Виртуализация таблицы (`VirtualScheduleGrid`) — проверить, что рендер не
  деградирует; сравнить ветку `codex-grid-gantt-performance`.
- Рендер Гантта и логического графа на больших объёмах.
- Размер бандла и время первой загрузки (Lighthouse на лендинге/`/app`).

**Выход:** бенчмарк-отчёт с порогами регрессии (например, CPM 5k < X мс).

## Фаза 8. CI/CD-ворота (закрепляем результат)

Собрать единый GitHub Actions pipeline (есть заготовки в `.github/workflows`):

```
lint  →  typecheck (strict)  →  unit+domain (vitest, coverage gate)
      →  migrations apply-from-scratch + supabase types diff
      →  build + bundle-size check
      →  e2e (playwright, demo)  →  security/secret scan
```

Правила: блокировать merge при падении любого этапа; порог покрытия ядра;
запрет роста числа strict-ошибок и циклических зависимостей (baseline-файл).

**Выход:** зелёный required-pipeline на `develop`, защита ветки.
